# 分支、提交、PR 与独立审查

本仓库通过带明确业务对象的开发分支组织词条、来源、权利、工具和发行变更。单个 PR 必须能独立审查、验证和回退；热梗新增、释义修订、出处或证据纠正必须一个热梗对应一个独立 PR，关联来源、权利记录、研究队列和索引同步纳入该热梗交付。工具、发行及仓库级基础设施变更按独立技术对象组织，不得作为批量热梗研究的例外。完成目标分支规则要求的检查后使用 squash 合并，已有已共享历史不为修饰说明而强制改写。

## 提交与标题

新增维护者提交、PR 标题和最终 squash 消息采用 `type(scope): 简体中文具体变更主题`。技术类型与受影响模块使用稳定英文标识，主体说明必须体现准确行为及对象；路径、词条名、API 和技术标识保留原文。禁止空泛更新、纯英文技术描述、伪合规汉字、不可见字符和用版本号替代真实变更。核心功能、来源权利、数据契约、权限和发行变更须有与影响相称的正文，说明问题、修复、影响与实际验证。

提交前可在 Git 私有钩子目录安装可信主分支的 `commit-msg` 校验器，不能执行检出分支中可变的钩子或校验脚本；推送后的 PR 校验必须覆盖全部新增提交和最终合并标题。本地钩子不等于远端强制保护，远端配置不生效时不可视为已经完成治理验收。

## PR 的完整性

正文明确：背景目标、受影响词条或具体代码、实现及行为变化、来源支持命题与适用权利、字段或用户兼容、测试结果、实际未完成项和恢复方式。创建前对照已有工作、准确 HEAD、完整 Diff、来源记录、变更边界及授权。来源与许可须有本仓库的可核验登记，并由可公开访问的原始资料支持。

实现者自查不替代独立审查。独立审查者读取原始差异、确切提交、权利与来源证据并覆盖代码、数据一致性、异常、失败恢复和传播边界。技术审查记录不等于 GitHub 平台批准；同一维护账号不能批准自己的 PR，不能为此设置永久无法满足的必需平台审批数。

公开审查正文只保留具体问题、代码定位、行为影响及对应复现。依赖其他 PR 的独立技术变更须先让依赖单独进入 main，再按本地入口中的依赖同步步骤以合规消息执行非快进合并，核对剩余差异、完整提交列表和最终 squash 消息，并以 main 为目标重新验收。各技术对象分别形成可回退的 squash 提交，同步提交适用相同的消息校验。具体步骤见[合并前检查](LOCAL-ENTRYPOINT.md#合并前检查与-squash)。

## 远端强制与变更处置

主分支通过 PR 合入变更，保留禁止直接推送、强推和删除的保护。合并须满足 `Project gate`、`Lifecycle gate`、`Release bytes gate` 三项必需检查、既有元数据校验和讨论解决要求，使用 squash。阻断讨论未解决、审查结论与 HEAD 不符、检查缺失或失败时不合并。

工作分支由已授权的 GitHub 身份发布，受保护的工作分支允许快进更新，保留禁止删除和非快进更新的保护。调整远端配置前须取得授权，核对完整规则及实际生效结果。

违规提交在本地修复；已共享历史不得仅为美化消息强改。违规 PR 能准确修复标题与正文则修复；变更范围错误则保留有效成果并按独立词条或逻辑对象拆分，正确替代后才按引用关系关闭旧 PR。模板、提交生成器和工作流造成的违规须修复其真实产生路径，并验证反例和合法邻例。

治理配置、审查脚本和工作流变更必须额外审查，不允许在同一 PR 中偷改检查名称、消除强制质量步骤或加入宽泛 bypass。本仓库质量契约禁止 `pull_request_target`。`verify.yml`、`local-lifecycle-verify.yml` 和 `release-byte-verify.yml` 保持只读，并继续承担三项强制质量门禁。正式发行使用独立的受控发布工作流：仅对指定版本和源码修订运行，写入权限局限于发行任务，发布前验证源文件与发行资产，发布后回读核对标签目标、发行说明及资产字节；不得以发行工作流替代或绕过三项质量门禁。元数据检查必须集成现有 `verify.yml`，从 PR 检出合并候选的真实 Git 提交历史和事件正文核验，并在项目验证结束时通过只读 API 核对当前标题、正文、两侧分支及提交、仓库和合并候选。新事件取消同一 PR 的旧验证运行；API 状态读取失败或与本次运行不符时检查失败。校验脚本和工作流随 PR 变更可能被修改，因此当前质量检查不能替代受保护规则、独立审查及检查来源防篡改，须继续核验远端正反例。
